## 1. 结论摘要

### 1.1 你以为的问题，其实不存在

"把 Python 学习和英语学习发布在一处"——**这件事已经做完了**。实测：

| | 现状 |
| --- | --- |
| 部署 | 一个 Cloudflare Pages 项目 `mian`，`/` = 萌码 Python，`/en/` = 萌语岛 |
| 数据库 | 同一个 D1 库 |
| 身份 | 同一张 `accounts` 表、**同一个 8 位同步码**管两个站 |
| 后端 | 共用 `api/_utils.js`（hash / 限流 / 鉴权），只按表名区分（`en_profiles`、`en_srs`…） |

后端去重已经很干净：英语站的账号接口就是一个 4 行文件，把 Python 站的实现原样再导出。

### 1.2 真正的问题有三个

1. **`/v2/` 是整套复制**——同一份代码在仓库里存了两遍，含约 931KB 逐字节重复的内容数据。
   这是唯一的结构性技术债。
2. **两个站之间没有任何链接**——物理上同处一个域名，却不是"一个产品"：
   从 `/` 找不到 `/en/`，从 `/en/` 也回不去。
3. **整个仓库都在被当成网站发布**——`README.md`、`schema.sql`、题库生成脚本、设计文档
   全部可以公开下载（已实测线上 200）。

### 1.3 阶段划分

| 阶段 | 做什么 | 用户可见的 URL 变化 | 风险 | 状态 |
| --- | --- | --- | --- | --- |
| **P0** | 源码移出发布目录 + 目录清理 | **无** | 极低（但有脚本陷阱） | ✅ 已完成 |
| **P1** | 消灭 `/v2/` 复制，合并成单一 Python 应用 | 仅 `/v2/`（302 兜底） | 低 | ✅ 已完成 |
| **P2** | `/` 改成统一大厅，Python 移到 `/py/` | `/`（唯一有书签风险的一步） | 中 | ⬜ 可选，未做 |
| **P3** | 文档与脚本收敛 | 无 | 极低 | ⬜ 未做 |

**P1 的价值最大、风险却很低**，因为它被刻意设计成**不碰 `/` 这个 URL**。
P2 是唯一会影响老用户书签的步骤，可以无限期推迟。

**P0 对线上零风险，但对你的测试套件不是**：它会让 8 个脚本静默指向错误的目录，
其中一个会"假装通过"。P0 的验收标准因此不是"部署成功"，而是
**"脚本还在测真东西"**（见 P0 一节末尾）。

## 2. 现状（实测事实）

### 2.1 部署拓扑

```
mian.lihaiyang.net/          →  萌码 Python（工作台）
mian.lihaiyang.net/v2/       →  萌码 Python（学堂模式，整套复制的第二个副本）
mian.lihaiyang.net/en/       →  萌语岛 English Island
```

发布方式：`pages_build_output_dir = "."`，即**仓库根目录就是网站根目录**。
`functions/` 也在仓库根，Cloudflare 把它编译成后端接口，不当作静态文件。

### 2.2 重复度量

`js/`（v1）与 `v2/js/`（v2）共 17 个文件：

- **9 个字节完全相同**：`audio-confetti` `cloud` `examples` `exercises` `lessons-adv`
  `lessons` `poster` `progress` `python-worker` `turtle-canvas` `zip-writer`
- **8 个已分叉**：`app` `editor` `examples-lib` `file-tree` `learn` `python-runner`，外加 `css/style.css`

逐字节重复的内容数据（最大的一块）：

| 文件 | 大小 | 状态 |
| --- | --- | --- |
| `exercises.js` | 837 KB | 两份完全一样 |
| `lessons.js` | 40 KB | 两份完全一样 |
| `lessons-adv.js` | 44 KB | 两份完全一样 |
| `examples.js` | 10 KB | 两份完全一样 |

**合计约 931 KB 是纯粹的重复。** `README.md` 自己就写着"维护提醒：v2 是完整副本，两份都要更新"；
提交历史里连续 5 个云同步 bug 修复，每个都得改两遍（`cloud.js`、`progress.js` 两边同步改）。

**关键认识**：v2 并不是一个不同的应用。它用的是**同一套 DOM**，靠 `body.mode-learn`
这一个 CSS 状态切换布局，编辑器和运行舞台都是原地复用、零改动。
复制它只是为了"先不动 v1"——所以这份复制**从一开始就不该存在**。

分叉的方向是明确的单向超集：

| | v1（`/`） | v2（`/v2/`） |
| --- | --- | --- |
| `learn.js` | 62 KB | **93 KB**（学堂面板 + 任务卡 + 模拟考） |
| `css/style.css` | 88 KB | **107 KB**（多 23 条 `mode-learn` + 9 条 `learn-panel` 规则，v1 里为 0） |
| 入口页 DOM | 多了 `learnModal` / `learnClose`（弹窗） | 多了 `learnPanel` / `judgeView` / `btnFocus` / `btnCompare` 等 15 个 id |

也就是说：**v2 的入口页 ≈ v1 的入口页，把"学习弹窗"换成了"内联学堂面板"。**

### 2.3 源码公开暴露（实测线上 HTTP 状态）

因为 `pages_build_output_dir = "."`，整个仓库都被上传成了静态资源：

```
/README.md                        200   27919
/schema.sql                       200    3701
/tools/gen_exercises.py           200    7339
/wrangler.toml                    200     281
/en/CONTRACT.md                   200   14427
/英语学习网站设计方案.md            200   58391
```

**没有真正的密钥泄露**：`CODE_PEPPER` 是 Pages secret，从未进仓库。
但有一处需要顺手加固：`functions/api/_utils.js` 里有个开发兜底值 `"mian-dev-pepper"`——
万一线上忘了配 secret，口令哈希就会用一个公开的 pepper。建议改成生产环境缺失即报错。

### 2.4 可以放心复用的资产（不要动）

整理之前先确认这些"地基"是好的，别误伤：

- **两站同源**：`/`、`/v2/`、`/en/` 都是同一个 origin，所以 `localStorage` / `IndexedDB`
  **本来就是同一个池子**。这意味着 **Python 换路径不会丢任何数据**（存储按 origin 隔离，不按路径）。
- **Python 站没有 manifest、没有 service worker**：没有已安装的 PWA 会被 URL 变更打断，
  最多是老书签需要多点一次。
- **英语站的 PWA 是相对路径的**：`manifest.webmanifest` 用 `start_url: "./index.html"`、
  `scope: "./"`。文件搬家不改 URL，PWA 不受影响。
- **后端已经去重**：英语站的 `account.js` 只是把 Python 站的实现再导出，共用 `_utils.js`。
- **`vendor/` 已经是共享的**：`v2/index.html` 与英语站都用 `/vendor/...` 绝对路径，
  25MB 的 Pyodide 在仓库里只有一份。已在代码里实测确认：Worker 用
  `importScripts('/vendor/pyodide/pyodide.js')` 绝对路径加载运行时，CodeMirror 与
  confetti 也全是 `/vendor/...`。**因此 Python 站无论放在 `/`、`/v2/` 还是 `/py/`，
  这个 25MB 运行时都不会失效**——这是"敢搬目录"的关键前提。
- **全站没有会失效的绝对路径**：实测两站对根路径的引用只有 Python 站的 `/vendor/*`
  与英语站的 `/api/en*`（后者是 Functions，位置不随静态目录变化）。

## 3. 目标结构

```
mian/
├─ public/                    ← 唯一会被发布的目录（pages_build_output_dir）
│  ├─ index.html              🏠 统一大厅：两张卡 +「上次你在…」继续
│  ├─ _headers  _redirects
│  ├─ py/                     🐼 萌码 Python（工作台 + 学堂模式合一）
│  ├─ en/                     🐼 萌语岛（文件搬家，URL 完全不变）
│  └─ vendor/                 CodeMirror / Pyodide / confetti（绝对路径共用）
├─ functions/                 ☁️ 必须在仓库根（Cloudflare 约定，已实测）
│  └─ api/
│     ├─ _utils.js            共用：hash / 限流 / 鉴权
│     ├─ py/{sync,account,share}.js
│     └─ en/{sync,account,share}.js
├─ db/
│  ├─ py.sql                  （原 schema.sql）
│  └─ en.sql                  （原 en/schema-en.sql）
├─ tools/
│  ├─ dev_server.py           共用本地服务器
│  ├─ py/                     Python 站的生成与测试脚本
│  └─ en/                     （原 en/tools/）
├─ docs/
│  ├─ 代码库整理方案.md        本文
│  ├─ en.md  en-contract.md
│  └─ 英语学习网站设计方案.md
├─ README.md                  仓库门面：两个站的总览 + 部署 + 守则（不再被发布）
└─ wrangler.toml              pages_build_output_dir = "public"
```

**为什么 `public/` 里放真文件而不是生成出来的副本**：这样"源码不公开"和"零构建"
可以同时成立，而且**不产生任何新的重复**——`public/en/` 里的文件就是英语站的文件本身，
不是从别处拷来的。代价只是改一次 `wrangler.toml` 和部署命令。

**为什么 `README.md` 留在仓库根**：GitHub 用根 `README.md` 当仓库首页。
P0 之后它位于 `public/` 之外，**自动就不再被发布了**——问题解决，位置不用动。
它的内容应该在 P3 拆成"两站总览 + 部署守则"（根）与"Python 站细节"（`docs/py.md`）。

| --- | --- | --- | --- |

| D5 | **`public/` 放真文件，不做生成副本** | 避免把 v2 那种"两份要同步改"的问题升级成全局问题 | 提交生成的 `dist/` 目录 |

## 5. 阶段执行

### P0 — 源码移出发布目录（零 URL 变更）

**目标**：让仓库根不再是网站根；网页文件进入 `public/`，源码留在外面。

**为什么对线上零风险**：这一步只改文件在磁盘上的位置，**不改任何 URL**。
`/`、`/v2/`、`/en/` 全部保持原样，`_headers` 里的路径前缀规则也因此不用改。
已端到端实测（见 9.1）。

**但它有一个不明显的陷阱**：仓库里 8 个脚本靠"目录层数"推断仓库根，
文件挪深一层后它们照常运行、却操作着错的位置——其中 `check_lessons.py` 会
**静默假绿**（退出 0、报告"0 课"，其实什么都没测）。
**搬完必须按下面那张表逐个修脚本，并确认它们还在测真东西。**

```bash
set -e
cd <仓库根>

# 1) Python 站的网页文件 → public/（vendor 也搬，URL 不变故所有 /vendor/... 引用照旧生效）
mkdir -p public
git mv index.html css js v2 vendor _headers public/

# 2) 英语站：只搬"网页文件"，源码留在 public/ 之外
mkdir -p public/en docs db
git mv en/index.html en/css en/js en/data en/assets en/img \
       en/sw.js en/manifest.webmanifest en/share.html  public/en/
git mv en/tools              tools/en
git mv en/README.md          docs/en.md
git mv en/CONTRACT.md        docs/en-contract.md
git mv en/schema-en.sql      db/en.sql

# 3) Python 站的源码归位
mkdir -p tools/py
git mv tools/exlib.py tools/gen_exercises.py tools/check_lessons.py tools/check_examples.py \
       tools/fix_families.py tools/fetch-vendor.sh tools/e2e_judge.mjs \
       tools/e2e_learn.mjs tools/e2e_learn_v2.mjs tools/e2e_sync.mjs tools/test_cloud_sync.mjs \
       tools/py/
git mv tools/ex_families_a.py tools/ex_families_b.py tools/ex_families_c.py \
       tools/ex_families_d.py tools/ex_families_e.py tools/py/
git mv schema.sql            db/py.sql
git mv 英语学习网站设计方案.md  docs/

# 4) 清理
rm -f 代码小助手少儿版.zip .DS_Store
rmdir assets                       # 实测为空目录，无任何引用
rmdir en                           # ⚠️ 必须写：git mv 不会删除被搬空的源目录，
                                   #    而空目录不被 git 跟踪，git status 是干净的——
                                   #    这个"隐形残留"会让 /en/ 返回 200 的目录列表而不是 404，
                                   #    从而掩盖真正的故障
```

### ⚠️ P0 必须同步修的脚本（这是 P0 真正的风险所在）

**根因**：仓库里几乎所有脚本都靠 `__file__` 的**目录层数**推断仓库根
（`dirname(dirname(__file__))` 之类）。文件往 `tools/py/`、`tools/en/` 挪深了一层之后，
这些脚本算出来的根就从"仓库根"变成了 `tools/`——**它们仍然会运行，但操作的是错的位置**。

这不是理论风险：以下每一处都在临时副本上**真实执行过**，`tools/py/check_lessons.py`
会出现**静默假绿**——退出码 0、打印"✅ 全部 0 课的示例代码都能跑通"，实际一节课都没校验。
**如果只改 `wrangler.toml` 和 `dev_server.py`，你的测试套件会通过，但它什么都没测。**

| 脚本 | 症状（已实测） | 修法 |
| --- | --- | --- |
| `tools/py/check_lessons.py` | 🔴 **静默假绿**：`找不到 js/lessons.js` → "全部 0 课" → 退出 0 | ROOT 改为 `<repo>/public` |
| `tools/py/check_examples.py` | 崩溃：读 `<repo>/tools/js/examples-lib.js`，退出 1 | 同上 |
| `tools/py/gen_exercises.py` | 默认写入模式崩溃（`<repo>/tools/js/` 不存在）；`--check` 侥幸通过 | ROOT 改为 `<repo>/public` |
| `tools/py/test_cloud_sync.mjs` | ROOT 算成 `tools/`，读 `tools/js/cloud.js` | 多退一层到仓库根，再拼 `public` |
| `tools/py/fetch-vendor.sh` | DEST 变成 `tools/vendor/pyodide` | 指向 `public/vendor/pyodide` |
| `tools/en/*.py`（6 个：`check_audio` `check_content` `check_fonts` `gen_audio` `gen_lessons` `gen_pairs`） | 原本 `dirname(dirname(F))` = `en/`，现在 = `<repo>/tools`；`gen_pairs` 会往 `tools/data/` 写、`check_fonts` 找 `tools/assets/fonts` | 每个文件加 `REPO` 常量，站点根指向 `public/en` |
| `tools/en/dev_server.py` | 🔴 **整个英语站本地预览不可用**：`/en/` 返回空目录列表 200、`/en/index.html` 与 `/en/data/lessons.js` 都 404 | 默认静态根改为 `<repo>/public`，并改 docstring 里的调用示例 |
| `tools/en/dump_data.mjs` | DATA 指向 `<repo>/tools/data` | 改为仓库相对 |

**两个容易漏的连带问题**：

1. `tools/en/check_content.py` 与 `tools/en/gen_pairs.py` 会 `spawn`
   `os.path.join(ROOT, "tools", "dump_data.mjs")`。ROOT 改成仓库根后会变成
   `tools/tools/dump_data.mjs`；而 `dump_data.mjs` 本身在 `tools/en/` 下。
   这里要**按仓库相对路径重写**（`<repo>/tools/en/dump_data.mjs`），
   不是简单改个 root 就行。
2. `tools/py/fix_families.py` **不用改**——它只用 `__file__` 找同目录的
   `ex_families_*.py`，而那几个文件跟它一起搬到了 `tools/py/`。
   别顺手"修"它。

**另外 2 处配置与 1 处注释**：

1. `wrangler.toml`：`pages_build_output_dir = "."` → `"public"`
2. 部署命令：`wrangler pages deploy . --project-name mian --branch main`
   → `wrangler pages deploy public --project-name mian --branch main`
   （**不能保留那个 `.`**，显式传目录会覆盖 `wrangler.toml` 里的设置）
3. `tools/en/e2e_sync.mjs` 的注释写着 `./en/schema-en.sql` → 改成 `./db/en.sql`

**改完必须验证脚本真的还在测东西**——不能只看退出码：

```bash
python3 tools/py/check_lessons.py | tail -3     # 必须显示 54 课，不是 0 课
python3 tools/py/check_examples.py | tail -3    # 必须是 145 个示例，退出 0
python3 tools/py/gen_exercises.py --check       # 必须仍是 1318 题
ls public/js/exercises.js                       # 确认题库还在站点根
```

**验证**：先起服务（`wrangler` 会自己读 `wrangler.toml` 里的 `pages_build_output_dir`），
**另开一个终端**跑下面的检查：

```bash

curl -s -D - -o /dev/null $B/vendor/codemirror/codemirror.min.js | grep -i cache-control
```

**源码泄露要用"内容断言"，不能用状态码**——这是本方案最容易写错的一条验收：

因为本站没有 `404.html`，Cloudflare Pages 对**任何未匹配的路径都会回落到
`index.html` 并返回 200**。所以 `/README.md`、`/wrangler.toml`、`/schema.sql`
在 P0 之后返回的是 **200 + 首页 HTML**，而不是 404。
用 `-w '%{http_code}'` 判断会得出"还是 200，没修好"的错误结论。

```bash
# 正确做法：证明返回的是首页回落，而不是源码正文
curl -s $B/README.md | grep -q '^# ' && echo "LEAK" || echo "OK（不是 markdown 正文）"
# 拿真实存在过的敏感串做断言（D1 database_id）
curl -s $B/wrangler.toml | grep -q 'c716860a' && echo "LEAK" || echo "OK"
curl -s $B/schema.sql    | grep -q 'CREATE TABLE' && echo "LEAK" || echo "OK"
```

**可选但推荐**：放一个 `public/404.html`。有了它，未匹配路径才会真的返回 404，
"没被发布"这件事才能用状态码断言——上一条的坑也就不存在了。

**两个 `wrangler pages dev` 的假警报，别被吓到**：

- `/_headers` 会返回 **502**（`ENOTDIR ... public/_headers/index.html`）。
  这是 dev server 对保留配置文件的怪癖，**不是配置错误**；它反而证明静态根已经是 `public/`。
  线上不会这样。
- 日志里的 `Parsed 10 valid header rules` 说明 `_headers` 被正确读取了。
- `/index.html` 会 **308 跳转到 `/`**，属正常行为。

然后跑第 6 节的全部测试。**先发一个预览分支确认**，别直接上 main：

```bash
wrangler pages deploy public --project-name mian --branch preview-restructure
# 用返回的预览 URL 复跑上面的 curl（尤其确认 /api/* 和 /en/ 正常），再合并到 main
```

**回滚**：`git revert` 该次提交即可（纯 `git mv` + `wrangler.toml` / 8 个脚本的路径改动，
没有内容改写）。**注意**：如果已经跑过 `git rm` 之类的删除，回滚同样能恢复，
因为删除前的内容都还在 git 历史里。

### P1 — 消灭 `/v2/` 复制，合并成单一 Python 应用

**目标**：v2 成为唯一正式版，v1 的弹窗式学习中心退休，`/v2/` 这个 URL 用 302 兜底。

**为什么风险低**：这一步**不动 `/`**。老用户的书签、`/p/{id}`、`/s/{id}` 分享短链全部不受影响。
只有 `/v2/` 这个由 README 宣传出去的较新 URL 会变成一次跳转。

**搬法**：把 v2 的 8 个分叉文件提升为正式版，覆盖根位置，然后删掉 `public/v2/`。

```bash

cd <仓库根>

# 1) 分叉文件：以 v2 为准，提升到根位置
git mv -f public/v2/index.html        public/index.html
git mv -f public/v2/css/style.css     public/css/style.css
git mv -f public/v2/js/app.js         public/js/app.js
git mv -f public/v2/js/editor.js      public/js/editor.js
git mv -f public/v2/js/examples-lib.js public/js/examples-lib.js
git mv -f public/v2/js/file-tree.js   public/js/file-tree.js
git mv -f public/v2/js/learn.js       public/js/learn.js
git mv -f public/v2/js/python-runner.js public/js/python-runner.js

# 2) 剩下 11 个字节完全相同的文件直接丢弃（根位置已有一份）
#    ⚠️ 必须加 -f：这些文件是被 git 跟踪且已在索引里有暂存改动（前面 git mv -f 动过它们），
#       不加 -f 会报 "the following files have changes staged in the index" 而失败
git rm -r -f public/v2
# git rm 只删它清空的目录，还会剩两个空目录，要显式收掉
rmdir public/v2/css public/v2 2>/dev/null || true

# 3) ⚠️ 必须换资源版本号 —— 这是 P1 最容易漏、且会真的弄坏老用户的一步

#    learn.js 62401→93252、style.css 88038→107273、app.js 52765→57662 …
#    浏览器/CDN 里缓存的还是 v1（弹窗版）的字节，配上新的内联学堂 HTML = 学习中心坏掉
sed -i '' 's/?v=20260914k/?v=20260915a/g' public/index.html

printf '/v2/*  /  302\n' > public/_redirects

# 5) 测试脚本跟着改（各 1 处，共 2 处）
sed -i '' 's|/v2/index.html|/|g' tools/py/e2e_learn_v2.mjs tools/py/e2e_sync.mjs
git rm tools/py/e2e_learn.mjs          # v1 弹窗测试，见下方「注意 2」
```

**注意三件事**：

1. **必须换资源版本号**（`README.md` 里的部署守则）：CDN 对 `/js/*`、`/css/*`
   有 4 小时默认缓存，会盖掉 `_headers` 的设置。要改两处：`public/index.html` 里

### P2 — 统一大厅（唯一有书签风险的一步）

**目标**：`/` 变成两个世界的入口；Python 移到 `/py/`；两站顶栏互相可达。

```bash
set -e
cd <仓库根>
mkdir -p public/py
git mv public/index.html public/py/index.html
git mv public/css public/js   public/py/
# public/index.html 新建为大厅页（两张卡 + 「上次你在…」继续）
# public/_redirects 增加：
#   /v2/*        /py/  302
#   保持 /p/* /s/* 不变（那是 Functions，与静态路径无关）
```

**`_headers` 必须同步改**（前缀规则不会互相覆盖，每条都要单独写，这是已知的坑）：

```
/js/*     →  /py/js/*
/css/*    →  /py/css/*
/vendor/* →  不变（仍在根）
/en/*     →  不变
新增大厅页如需特殊缓存策略，单独加 `/index.html`
```

**P2 必须同步改的 3 处硬编码根路径**（这是 P2 最容易漏、且会**功能性损坏**的地方，已逐处实测定位）：

| 位置 | 现在 | 必须改成 | 不改的后果 |
| --- | --- | --- | --- |
| `functions/s/[id].js` | `href="/?share=<id>"`（"🚀 在萌码里打开"按钮） | `/py/?share=<id>` | 家长点"在萌码里打开"会落到大厅，**分享的代码永远不会被打开** |
| `functions/_page.js` | `<a href="/">打开工坊</a>`（分享页页脚） | `/py/` | "打开工坊"不再指向工坊 |
| `public/index.html`（新大厅） | — | 建议加 `#code=` 转发（共 3 行） | 见下 |

**关于 `#code=` 旧链接——实测结论是"风险低但值得花 3 行买保险"**：

- `buildShareUrl()`（生成 `#code=` 链接的那个函数，用 `location.origin + location.pathname`）
  在 v1 和 v2 里**都已经是死代码——全仓库零调用者**。当前真正在用的分享方式是
  服务端短链：`CloudSync.shareCurrentFile()` → 后端返回 `/s/<id>` 或 `/p/<id>`。
  所以**现在没有代码在产出 `#code=` 链接**，不必为它做重活。
- 但它的**读取端仍然是活的**：入口页启动时会调用 `loadSharedCodeFromUrl()`
  解析 `#code=`。所以历史上可能存在的旧链接仍会被尝试解析——
  而 P2 之后它们会落到大厅，大厅不解析，于是静默失效。
- 因此：在大厅加一段 JS（检测 `location.hash` 以 `#code=` 开头就
  `location.replace("/py/index.html" + location.hash)`）**是便宜的保险，建议加**。
  注意 **URL 的 fragment 永远不会发给服务端**，`_redirects` 无法处理它，只能靠 JS。
- P3 可以顺手把 `buildShareUrl` / `loadSharedCodeFromUrl` 这一对死代码删掉，
  删了就不需要这段转发逻辑了——两者选一个即可。

三种分享形态在 P2 后的兼容性结论（已逐处实测确认）：

- `?share=<id>` 短链：走 `fetch("/api/share?id=...")`，**绝对路径指向 Functions**，
  与静态目录无关；只要按上表把落点改成 `/py/` 即可 ✅
- `/s/<id>`、`/p/<id>` 分享页：由 `functions/s/`、`functions/p/` 提供，**位置不受 P2 影响** ✅
- `#code=` 长链：仅剩读取端是活的，按上面 3 行转发即可 ✅（不处理则静默失效）

**降低"书签落到大厅"的突兀感**：大厅记住用户上次进的世界，顶部放一张
「继续上次：萌码 Python」的卡并支持自动续跳。因为三处同源，
大厅**可以直接读两站的 localStorage**——这也是后续做"家长中心"（一处看两个站的进度）的天然基础。

**验证**（P2 的验收必须覆盖分享链路，那是唯一会功能性损坏的地方）：

```bash
wrangler pages dev --port 8791
# 1) 大厅与两个站都在
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8791/           # 200 大厅
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8791/py/        # 200 Python
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8791/en/        # 200 英语
# 2) 老 URL 兜底
curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' http://127.0.0.1:8791/v2/index.html
# 3) 缓存策略跟着目录走（P2 最容易静默失效的一项）
curl -s -D - -o /dev/null http://127.0.0.1:8791/py/js/app.js | grep -i cache-control
# 4) COOP/COEP 仍在（没有它 Python 的 input() 直接不可用）
curl -s -D - -o /dev/null http://127.0.0.1:8791/py/ | grep -i cross-origin
# 5) 分享页的"在萌码里打开"落点正确 —— 改完 functions/s/[id].js 后人工点一次
#    或 grep 确认已无裸 "/?share=" 残留：
grep -rn '"/?share=\|href="/"' functions/
```

**P2 的硬性红线**：上面第 3、4、5 条全过。第 5 条尤其别只看代码——
它是一条"页面渲染正常、但点了按钮什么都不会发生"的静默故障。

**为什么这一步可以无限期推迟**：它不影响任何功能，只是信息架构更清晰。
P0、P1 已经拿走了绝大部分收益。

**回滚**：`git revert`，URL 恢复为 `/` = Python、`/en/` = 英语。

## 7. 必须遵守的既有约束（踩过一次的坑）

整理过程中最容易被打破的既有约定，逐条列出：

1. **改完 css/js 必须同时改资源版本号**。CDN 对 `/js/*`、`/css/*` 用 4 小时默认缓存，
   会盖掉 `_headers` 里的设置。改文件不改 URL ⇒ "新 HTML + 旧 CSS" 错版。
   涉及 `public/index.html` 的 `?v=` 与 `public/js/learn.js` 的 `const V`。
2. **`_headers` 的路径前缀规则不会互相覆盖**，每条都得单独写。
   P2 移动目录后 `/js/*`、`/css/*` 必须跟着改成 `/py/js/*`、`/py/css/*`，否则缓存策略静默失效。
3. **Python 站依赖 COOP/COEP**（`SharedArrayBuffer` 是 `input()` 同步阻塞的前提）。
   这两个头由根级 `/*` 规则提供，任何目录调整后都要用 `curl -D -` 复验一次。
4. **`/vendor/*` 是 immutable 强缓存**：`pyodide-lock.json` 内容一变就必须换 URL
   （现在靠 `lockFileURL: "...?v=2"`），否则老用户会一直读到旧 lockfile。
5. **不要给 Python 暴露 `__` 开头的 JS 全局名**：Python 类体里会被名字改写成
   `_类名__foo`，看起来像"方法不存在"。
6. **判题超时由主线程写 SIGINT**：Worker 自己的定时器不会触发。
   迁移时 `python-runner.js`（主线程）与 `python-worker.js`（Worker）必须成对搬，别只搬一个。

- **不引入 npm / 打包器 / ESM**。"零构建"是刻意决策，改完直接部署是它最大的优点。
- **不抽 `public/shared/`**。理由见 D3：两站的同名模块数据模型不同，合并是负收益。
- **不合并两站的 `cloud.js` 同步协议实现**。协议相似（rev + LWW + 墓碑）但表结构与
  实体不同，共享 `_utils.js` 这一层已经是合适的复用粒度。
- **不动 `functions/` 的位置**。它必须在仓库根，Cloudflare 才有正确的路由发现
  （已用 `wrangler 4.130.0` 实测：`pages_build_output_dir = "public"` +
  根级 `functions/`，`/api/*` 正常响应）。
- **不改 `_headers` 里的 COOP/COEP 与 immutable 缓存策略**，除非文档明确要求。
