# 萌学园：多学科学习平台架构设计

> **读者**：接手这个项目的工程师 / AI agent，以及做产品决策的家长本人。
> **读完能做到**：知道平台怎么分层、加一个新学科需要动哪些文件、每个学科的
> 技术难点在哪、按什么顺序做不会把线上两个站搞坏。
> **基线**：P0/P1 已完成（源码与产物分离、v2 合并），线上 `/` 是萌码 Python、`/en/` 是萌语岛。
> 相关文档：`docs/代码库整理方案.md`（怎么走到今天的、以及 P2/P3 的收尾）。

## 1. 结论先行

### 1.1 一句话架构

**一个 Cloudflare Pages 项目 + 一个 D1 库 + 一套共用身份，托管一个"大厅 + N 个学科岛"。**

现在的两个站已经是这个形状的雏形（`/` 和 `/en/`，共用 8 位同步码）。
这次设计要做的是三件事：

1. **把 `/` 让出来做大厅**（原计划里的 P2），学科各自进自己的目录；
2. **把两个站里重复的那一层抽成"平台层"**（成长系统 / 云同步 / UI / 音频 / 存储），
   否则加 5 个学科 = 把今天 v2 那种"整份复制"的债乘以 5；
3. **定义"学科契约"**——加一个新学科应该只是加一个目录 + 一份声明，
   而不是再写一遍等级、徽章、同步、家长报告。

### 1.2 必须先说清楚的一件事：**代码不是成本，内容才是**

今天两个站的代码量并不大，但内容量是这样的：

| 学科 | 已有内容 | 生成方式 |
| --- | --- | --- |
| 萌码 Python | 54 课教程 + 145 个示例 + **1318 道练习题** + 20 套模拟考 | `tools/py/ex_families_*.py` 生成，**答案真的跑一遍** |
| 萌语岛 | 600 词 + 100 句型 + 20 本分级绘本 + 30 关拼读 + 20 对最小对立 | 词库手写 + `gen_lessons.py` / `gen_audio.py` 生成 |

**新增一个学科的代码可能只要 1–2 周，但内容要到"能给孩子用"的密度，通常是 1–3 个月。**
所以本设计的重点是：**让代码这一侧尽量便宜、可复用**，把预算留给内容。
任何"为了架构好看而增加内容生产成本"的方案都应该被否决。

### 1.3 路线图速览

| 阶段 | 做什么 | 产出 | 风险 |
| 阶段 | 做什么 | 产出 | 风险 | 状态 |
| --- | --- | --- | --- | --- |
| **M0** | 大厅 + 学科目录化 + 设计令牌 | `/` 变成大厅，Python 进 `/python/` | 中 | ✅ 已完成 |
| **M1** | 抽平台层 | 一份 `shared/`，两个老站改成它的第一个和第二个用户 | **高（动线上代码）** | 🟡 **内核已完成**，老站迁移未做（见 9.1） |
| **M2** | 第一个新学科：**打字** | 证明"加学科 = 加目录" | 低 | ✅ 已完成（36 项 e2e） |
| **M3** | **数学** | 需求最大的一科 | 中（内容量大） | ⬜ 未做 |
| **M4** | **拼音 → 语文** | 数据重（音频 / 笔顺） | 中高 | ⬜ 未做 |
| **M5** | **C++** | 把"运行代码"做成能力插件 | 中（方案已验证：Runno，按需加载 ≈14.2 MB） | ⬜ 未做 |
| **M6** | 家长中心 | 跨学科周报，这才是"一处"的真正价值 | 低 | ⬜ 未做 |

**M1 是全盘风险最高的一步**（要改两个有真实孩子在用的站），但它也是
"以后每加一科都便宜"的前提。所以它必须小步做、由现有的 e2e 断言护着。

**实际执行时把顺序调换了一下**，理由见 9.1：先让**新学科**（打字）当平台层的
第一个用户来验证契约，再考虑迁移老站——设计文档原本写的是"先迁英语站"，
但那等于在契约还没被验证之前就动一个有真实孩子在用的站。

## 2. 现状盘点：哪些能复用、哪些是债

### 2.1 可以直接复用的资产

| 资产 | 现状 | 对新平台的意义 |
| --- | --- | --- |
| 共用身份 | `accounts` 表 + 8 位同步码，一个码管所有站 | **平台地基已经在了**，不用重新设计账号 |
| 同源 | `/`、`/en/` 同 origin，localStorage/IndexedDB 是同一个池子 | 大厅和家长中心**可以直接读所有学科的数据**，不需要跨域或后端聚合 |
| 零构建 | 原生 JS，IIFE 挂 `window`，无 npm / 无打包 | 改完直接部署，这是最大的运维优势，不要丢 |
| 自托管 `vendor/` | 25MB（Pyodide / CodeMirror / confetti），绝对路径引用 | 多学科共用同一份，不重复下载 |
| 判题引擎 | `PythonRunner.judge(code, stdin, timeout)`，主线程 SIGINT 中断 | 抽象成 `capabilities/judge`，Python 是第一个实现，C++ 可做第二个 |
| 内容管线范式 | **期望答案是跑出来的，不是手写的**（`exlib.py` 真跑参考答案） | 这个原则要推广到数学（用 Python 算答案）等学科 |
| 分享 / 短链 | `/s/{id}` `/p/{id}` + D1 `shares` 表 | 加个 `subject` 字段就能全平台共用 |
| SOPS/记忆盒 | 英语站的 Leitner 5 盒 | 抽成 `capabilities/srs`，语文/拼音/英语共用 |
| 音频精灵 | 一个主题合成一个 m4a，`currentTime` 定位，零延迟 | 拼音/语文/英语共用同一套播放器 |
| e2e 测试 | 97 项断言（80 + 8 + 9），跑在真实部署上 | **M1 重构的安全网**，价值极高 |

### 2.2 要还的债（不还就会 ×N 放大）

1. **成长系统写了两遍**：`public/js/progress.js`（60KB）和 `public/en/js/progress.js`（33KB）
   都在做"档案 + 经验等级 + 连续打卡 + 每日任务 + 徽章 + 奖牌 + onChange + 导出/导入行"。
   两边的 API 长得几乎一样：
   - Python：`init / reload / onChange / recordRun / recordLesson / recordQuiz / getMissions / getBadges / getMedals / levelInfo`
   - 英语：`profiles / switchProfile / addXp / level / streak / daily / claimDaily / missions / badges / medals / markWord / markLevel / exportRow / importRow / reset`
   
   **共同内核是清楚的，只是领域事件不同。** 再复制 5 遍就是灾难。

2. **同步协议写了两遍**：都用 `rev + updated_at LWW + 软删除墓碑`，
   只是实体名不同——
   - Python：`{profiles, folders, files, progress, vfs, learn}`
   - 英语：`{profiles, progress, srs, daily}`
   
   协议本身是通用的，重复的是实体清单和表名。

3. **两套视觉语言**：Python 是"奇幻工坊"（深色/亮色、霓虹），英语是"旅行手账 ×
   丝网印刷贴纸"（米色纸感）。**多学科必须有一套统一的设计令牌**，否则大厅会像
   五个不同网站拼起来的。

4. **全站 COOP/COEP 过宽**：见 6.1，这是给未来埋的雷。

## 3. 目标结构

### 3.1 磁盘 = URL，一层学科目录

```
public/                        ← Cloudflare Pages 的发布根（唯一被上传的目录）
├── index.html                 🏠 大厅：所有学科 + 继续上次 + 家长中心入口
├── _headers  _redirects       缓存策略 / 老链接兜底
├── shared/                    🧩 平台层（全站唯一一份，被所有学科引用）
│   ├── core/
│   │   ├── registry.js        学科注册表：读 manifest、渲染大厅、学科切换
│   │   ├── profile.js         统一档案：一个小朋友跨所有学科
│   │   ├── progress.js        成长内核：XP / 等级 / 连续打卡 / 每日任务 / 徽章 / 奖牌
│   │   ├── sync.js            通用云同步：rev + LWW + 墓碑，实体由学科声明
│   │   ├── store.js           localStorage / IndexedDB 封装、命名空间、配额、迁移
│   │   └── bus.js             事件总线（学科 ↔ 平台 ↔ 大厅）
│   ├── capabilities/          可插拔能力（谁声明谁加载，按需懒加载）
│   │   ├── judge.js           判题：Python 已实现；C++ 未来接入
│   │   ├── srs.js             记忆盒（Leitner）：英语/语文/拼音共用
│   │   ├── typing.js          键盘引擎：WPM / 准确率 / 指法热力图
│   │   ├── stroke.js          笔顺渲染：语文
│   │   └── speech.js          录音 + 本地节奏/音高评测：英语/拼音
│   ├── ui/
│   │   ├── ui.js              组件：卡片/弹窗/贴纸/印章/撒花/toast
│   │   └── audio.js           音效合成 + TTS 兜底 + 音频精灵播放器
│   └── styles/
│       ├── tokens.css         设计令牌（颜色/圆角/字体/间距/阴影/暗色）
│       ├── base.css           重置 + 布局骨架
│       └── components.css     组件的公共样式
├── python/                    🐼 萌码 Python（工作台 + 内联学堂）
├── en/                        🐼 萌语岛（**URL 不动**，已装 PWA）
├── math/                      🔢 数学
├── pinyin/                    🅰️ 拼音
├── chinese/                   📖 语文
├── typing/                    ⌨️ 打字
├── cpp/                       ⚙️ C++（未来）
├── parent/                    👨‍👩‍👧 家长中心（跨学科周报）
└── vendor/                    CodeMirror / Pyodide / confetti / 未来的编译器
```

**为什么 `shared/` 不叫 `_shared/`**：以 `_` 开头的目录在 Cloudflare Pages 上是否
被排除上传没有实测过，赌不起。叫 `shared/` 零风险（它本来就要被浏览器下载，公开无妨）。

**为什么学科目录不再套一层 `subjects/`**：磁盘路径直接等于 URL，
少一层心智负担，且 `/en/` 原地不动就能继续用（已安装的 PWA 不会断）。

### 3.2 URL 命名

| 学科 | URL | 说明 |
| --- | --- | --- |
| 大厅 | `/` | 现在的萌码 Python 让位 |
| Python | `/python/` | 从 `/` 迁出；`/py/*` 做 302 别名兜底 |
| 英语 | `/en/` | **冻结不改**。已安装 PWA 的 `scope` 绑在这里 |
| 数学 | `/math/` | |
| 拼音 | `/pinyin/` | 用全词，避免和 `/py/`（Python）混淆 |
| 语文 | `/chinese/` | |
| 打字 | `/typing/` | |
| C++ | `/cpp/` | |
| 家长中心 | `/parent/` | |

`/v2/*` → `/python/`（已有的重定向改个落点）。

## 4. 平台层设计（本次的核心）

### 4.1 学科契约：加一科 = 加一个目录 + 一份声明

每个学科提供一个 `subject.js`（跟在 HTML 里，零构建）：

```js
// public/math/subject.js
Platform.register({
  id: "math",
  name: "数学岛",
  emoji: "🔢",
  accent: "#3B82F6",              // 学科主色，只覆盖令牌里的一个变量
  url: "/math/",
  grades: [1, 2, 3, 4, 5, 6],     // 覆盖年级
  tagline: "每天 15 分钟，把算术练成直觉",
  capabilities: ["judge"],         // 声明要用哪些平台能力（决定懒加载什么）
  storage: { ns: "math" },         // 存储命名空间：mian_math_*

  // 学科自己的领域事件 → 折算成 XP 与计数（平台不用懂"做题"是什么）
  events: {
    solve:      { xp: 10, counters: ["solved"] },
    perfect:    { xp: 25, counters: ["perfect"], when: e => e.allCorrect },
    streakDay:  { xp: 5,  counters: ["days"] },
  },

  // 徽章 / 奖牌 / 任务 / 每日：声明式，平台负责判定与展示
  badges:  [{ id: "math_speed_100", title: "闪电口算", emoji: "⚡", when: s => s.solved >= 100 }],
  medals:  [{ id: "math_l1_gold",   title: "一年级金牌", tier: "gold", when: s => s.l1Done }],
  missions:[...], daily: [...],

  // 给家长中心的一行摘要（家长中心不关心学科内部结构）
  parentSummary(s) {
    return { 掌握: s.solved, 正确率: pct(s.correct, s.solved), 薄弱: weakestTopics(s) };
  },
});
```

平台读到这份声明后，**自动**获得：经验/等级/连续打卡/每日任务/徽章墙/奖牌墙/
云同步/家长摘要。学科作者只需要专心写"题目"和"界面"。

> 这是整个设计里最重要的一个抽象。判断标准很简单：
> **加第 7 个学科时，如果还要改 `shared/` 里的代码，说明契约没设计好。**

### 4.2 成长系统：三层，一次实现

```
┌─ 跨学科层（大厅 / 家长中心）──── 总等级 = f(各科 XP)、全站徽章、跨科连续打卡
├─ 学科层（各学科自己）─────────── 本学科等级、进度地图、分科徽章/奖牌
└─ 内核层（shared/core/progress.js）─ 档案、XP 曲线、打卡、每日任务、判定、持久化、导出/导入
```

从两个现有实现里能明确提炼出的共同内核：

- **档案**：`profiles`（多小伙伴）、切换、改名、换头像
- **经验**：`addXp(n)` → `levelInfo(xp)`（等级曲线、称号、进度条）
- **连续打卡**：`streak` / `touchToday()`
- **每日任务**：`daily`（3 条）、`claimDaily()`、跨天滚动
- **判定**：`checkBadges()` / 任务完成 / 奖牌发放，返回"本次新获得的"
- **持久化**：命名空间化的 localStorage + IndexedDB
- **同步接口**：`exportRow()` / `importRow(row)` / `exportDaily()` / `importDaily()` / `reset()`
- **通知**：`onChange(fn)`

学科只提供声明（`events` / `badges` / `medals` / `missions` / `daily`），
内核负责剩下全部。**这套东西现在有 93KB 的两份实现，合并后应显著更小。**

**跨科连续打卡**的定义要小心：不能因为"今天只学了数学"就断掉英语的连续记录，
也不能让打卡变成刷同一道题。建议：
- 学科内 `streak` 照旧（本学科连续天数）
- 平台级 `总打卡` = 当天任一学科有实质学习行为（≥1 个 `events` 计数，且有最小时长阈值）
- 每日任务仍然是**每科 3 条**，大厅显示"今天还有 2 科没碰"

### 4.3 云同步：一份实现，实体由学科声明

现有两套协议的形状是完全一样的：

```
GET  /api/…/sync?code=&pin=&since=<rev>   增量拉取（rev 是账号级单调版本号）
POST /api/…/sync { rows: { entity: [ … ] } }  按行 updated_at 做 LWW，删除用墓碑
```

差异只有**实体清单**和**表名**。所以：

- 前端：`shared/core/sync.js`，参数是 `{ endpoint, entities, namespace }`
- 后端：新学科统一走一个通用端点，落到一张通用表（见第 5 节）
- **老学科原样保留** `/api/sync` 与 `/api/en/sync`，不迁移，零风险

### 4.4 设计系统：一套令牌 + 每科一个主色

两个站现在是两套视觉语言。多学科必须收敛成一套，做法是
**共享全部设计令牌，学科只覆盖 `--accent` 系列**：

```css
/* shared/styles/tokens.css */
:root {
  --bg: …; --paper: …; --ink: …; --muted: …;
  --radius-card: 18px; --radius-chip: 999px;
  --font-ui: "Noto Sans SC", system-ui, sans-serif;
  --font-mono: "JetBrains Mono", ui-monospace, monospace;
  --space-1: 4px; … ; --shadow-card: …;
  /* 学科主色：默认值，学科页覆盖 */
  --accent: #6A4C93; --accent-soft: …; --accent-ink: #fff;
}
```

```html
<!-- public/math/index.html -->
<link rel="stylesheet" href="/shared/styles/tokens.css">
<link rel="stylesheet" href="/shared/styles/base.css">
<link rel="stylesheet" href="/shared/styles/components.css">
<link rel="stylesheet" href="css/math.css">   <!-- 只写本科目特有样式 -->
<style>:root{ --accent:#3B82F6; --accent-soft:#DBEAFE; }</style>
```

大厅用它来给每个学科上色（卡片、图标底色），孩子一眼能把"数学"和"语文"区分开，
但整体是同一个产品。**英语站的"手账风"要不要收敛**是个产品决策，见第 10 节。

### 4.5 能力插件：按需加载，学科不该为用不到的东西付费

`capabilities` 里声明的才会加载。例如打字学科不声明 `judge`，就永远不会下载 Pyodide
（25MB）。这对小学生的网络环境是硬要求。

| 能力 | 现在在哪 | 谁会用 |
| --- | --- | --- |
| `judge` | Python 的 `python-runner.js` + `python-worker.js` | Python（已有）、C++（未来） |
| `srs` | 英语的 `srs.js`（Leitner 5 盒） | 英语、语文、拼音 |
| `typing` | 新写 | 打字，以及 Python/C++ 的"敲代码"练习 |
| `stroke` | 新写（需要笔顺数据） | 语文 |
| `speech` | 英语的 `speech.js`（录音 + 包络互相关） | 英语、拼音 |
| `audio` | 英语的 `player.js`（音频精灵）+ `audio-fx.js`（合成音效） | 几乎所有学科 |

**注意 `speech` 的诚实边界**：现有的本地评测只能判断"读没读、读完没、节奏像不像、
快慢、音量、停顿"，**不能判断音准**——所以界面上绝不给假的音准分。
拼音的**声调**比英语的节奏更接近"音高"，本地可以做基频包络（F0）比对，
这是**新能力**，需要单独验证，不要直接承诺。

## 5. 数据模型

### 5.1 现状

```
accounts                 ← 两站共用（8 位同步码，服务端只存 hash + pepper）
rate                     ← 限流，共用
profiles/folders/files/progress/vfs/learn/shares   ← Python 站
en_profiles/en_progress/en_srs/en_daily/en_shares  ← 英语站
```

**问题**：再加 5 个学科不能变成 5 套 `xx_profiles / xx_srs / …`。

### 5.2 目标：通用行表 + 少量专用表

```sql
-- 已有，不动
accounts(id, code_hash, pin_hash, nickname, avatar, rev, created_at, last_seen)
rate(...)

-- 跨学科统一档案（Python 已有 profiles，英语的 en_profiles 后续并入）
profiles(account_id, profile_id, nickname, avatar, created_at, updated_at, deleted_at, rev)

-- ★ 新增：所有学科的"状态"都走这一张表
--   entity: progress | srs | daily | draft | custom…
--   payload_json: 学科自定义，服务端不理解内容（和现在一样是黑盒）
sub_rows(
  account_id, subject, profile_id, entity, row_id,
  payload_json, updated_at, deleted_at, rev,
  PRIMARY KEY (account_id, subject, entity, row_id)
)

-- 代码类学科（Python / C++）的"作品"，两者模型一致，共用
works(account_id, subject, profile_id, folder_id, name, content, updated_at, deleted_at, rev)

-- 分享页：加 subject 就能全平台共用
shares(id, subject, kind, title, content, created_at, revoked, views)
```

**为什么 `payload_json` 是黑盒**：现在的同步就是黑盒（`stats_json` 等），
服务端只做 LWW 和墓碑。保持这一点，**加学科完全不需要动后端**，
也不需要 D1 迁移——这是"加一科很便宜"的关键。

### 5.3 迁移策略（有真实孩子在用的数据，必须稳）

| 数据 | 策略 |
| --- | --- |
| `accounts` / `rate` | 不动 |
| Python 的 `files` / `folders` / `vfs` / `learn` | **不动**，继续走 `/api/sync` |
| 英语的 `en_*` | **不动**，继续走 `/api/en/sync` |
| 新学科 | 走 `/api/v1/sync?subject=` + `sub_rows` |
| 将来的统一 | 用一次性脚本迁移，**双写 + 比对**验证后再切读 |

**明确不做**：为了"数据模型好看"而重写两个老站的同步。收益是审美，
代价是可能弄丢孩子的作品和进度。

## 6. 关键技术约束与风险

### 6.1 COOP/COEP 现在过宽，应该收窄

`public/_headers` 现在对 `/*` 发：

```
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

这两个头的**唯一目的**是让 `SharedArrayBuffer` 可用，而只有 Python 的
`input()` 同步阻塞需要它。代价是 **`require-corp` 会拦掉所有不带 CORP/CORS 头的
跨源子资源**——图片、字体、iframe、嵌入视频全都得自己托管。

今天没事（本来就全自托管），但一个"多学科平台"迟早要嵌第三方内容
（地图、词典、视频、可交互课件），到时候会**静默挂掉**，而且很难查。

**建议**：改成按路径发，只给真正需要 SAB 的学科：

```
/python/*     → COOP + COEP
/cpp/*        → COOP + COEP
其余          → 不发（或只发 COOP: same-origin）
```

改完之后 `/en/` 也能自由用第三方资源。**这一步应该在 M0 做**，
因为它是"松绑"，越早越好；而且 `_headers` 已经在 P0 验证过按路径生效。

### 6.2 零构建的边界：版本号会越来越痛

现在改完 css/js 必须手动改 `?v=` 和 `const V`（CDN 对 `/js/*`、`/css/*`
强制 4 小时缓存并盖掉 `_headers`）。两个站还能忍，**7 个学科 + 一个共享层就不行了**：

- 改了 `shared/core/progress.js` → 要改**所有**学科的 HTML 版本号，漏一个就出现
  "新共享层 + 旧学科页"的错版
- 这种错版**只在老用户身上复现**，本地永远是好的

**建议**：加一个 `tools/py/stamp.mjs`（**不是打包器**，只是一个批量替换版本号的脚本），
从文件内容的 hash 生成版本号，写进各学科 HTML。它仍然是零构建——
产物就是源文件本身，只是版本号自动化了。这是 M1 必须一起做的事。

### 6.3 各学科的硬骨头（已实测核实，不再是猜测）

| 学科 | 真正的难点 | 核实结论 |
| --- | --- | --- |
| **C++** | 浏览器内编译/执行 | ✅ **可行**：Runno（MIT）自托管，**约 14.2 MB（brotli 传输）**，交互式 `cin` 可用。见 7.7 |
| **语文** | 笔顺数据的体积与授权 | ✅ **可行**：3500 常用字 **约 4 MB gzip**；APL 授权，非传染性。见 7.5 |
| **拼音/语文** | 中文 TTS 可靠性 | ⚠️ **比预想更差**：安卓微信/QQ 内置浏览器**完全没有**这个 API。音频必须自托管。见 7.4 |
| **拼音** | 字→拼音数据 | ✅ 便宜：`mozillazg/pinyin-data`（MIT），8105 字 **62 KB gzip**，含多音字 347 KB |
| **数学** | 竖式 / 几何呈现（SVG）、答案校验 | 可控（生成时用 Python 算答案） |
| **打字** | 基本无难点 | 可控；中文打字先不做（输入法不可控） |
| **英语/Python** | 已经做完，只需接进平台层 | 可控 |

### 6.4 内容生产是主成本（再强调一次）

新学科的排期应该按**内容量**估，不是按代码量。参考基准：
一个学科要有"每天 15 分钟、能撑一个学期"的密度，大约需要
**100+ 关 / 500+ 题 / 配套音频或图解**。建议每个学科都先做
**一条完整的最小纵向切片**（一关、能记录、能同步、能拿徽章），
验证管线跑通，再批量灌内容。

### 7.4 🅰️ 拼音

- 内容：声母 23 / 韵母 24 / 整体认读 16、四声、拼读、轻声、变调
- 题型：听音选拼音、看拼音选字、标声调、拼读跟读、声调听辨（最小对立对，如
  `mā / má / mǎ / mà`）

#### ⚠️ 音频必须自托管，这不是"优化"而是硬要求（已核实）

原先的设计里我写的是"音频是核心且必须自托管"，理由写得比较含糊。
核实之后结论更硬：**系统 TTS 不能作为中文内容的主要音源**，原因是：

| 平台 | 中文 TTS 可用性 | 证据 |
| --- | --- | --- |
| **安卓微信 / QQ 内置浏览器（WebView）** | ❌ **API 根本不存在** | MDN 兼容数据 `webview_android: false`。对国内小学生这可能是最大的一块流量 |
| **iPad / iPhone（都是 WebKit）** | ⚠️ 能发声，但**无法检测**，且可能只有机械音 | WebKit `appendVoices()` 只收录 `isSystemVoice` 的语音，导致下载的中文语音**列不出来**（WebKit bug 250665 / 290497，iOS 18 仍在）。要命的是 `speak()` 在零语音列表时**仍可能成功**，所以**没法做特性检测** |
| **Chrome on Windows** | ⚠️ 取决于是否装了中文语音包 | 走 SAPI |
| **Chrome on Android** | ⚠️ 取决于设备 | 走系统 `TextToSpeech`，可能是 `LANG_MISSING_DATA` |
| **任意 Chromium** | ⚠️ `speak()` 需要用户手势 | Blink 的 `IsAllowedToStartByAutoplay()` 门控，页面加载时不能自动读 |

**结论**：核心字音/拼音音频**必须预先合成并自托管**，沿用英语站已经验证过的
**音频精灵**方案（一个类别合成一个 m4a，用 `currentTime` 定位，零延迟、一次请求）。
系统 TTS 只作为**兜底**保留。

省钱的做法：普通话只有约 1300 个不同音节。按**音节拼接**（而不是逐字录音）
可以把音频体积压得很小——但这条路的音质和连读自然度**尚未验证**，
做之前先录一组样本试听。

#### 字 → 拼音数据（便宜，已核实）

用 `mozillazg/pinyin-data`（**MIT**）：

| 文件 | 内容 | 体积 |
| --- | --- | --- |
| `kMandarin_8105.txt` | 通用规范汉字表 8105 字，每字一个常用读音 | 168 KB → **62 KB gzip** |
| `pinyin.txt` | 44435 字，**含多音字**（`行 → xíng,háng,…`） | 985 KB → **347 KB gzip** |
| `kHanyuPinlu.txt` | 3799 字，**按词频排序** | 79 KB |

只用前者就够开拼音学科；要多音字辨析再加 `pinyin.txt`。
**不要用 `hotoo/pinyin` 的 npm 包**——它 unpacked 有 59 MB，而裸数据文件只要 350 KB。

#### 声调评测是新能力，不要照搬英语那套

英语的本地评测做的是"节奏包络互相关"，**声调需要基频（F0）包络**比对，
原理上可行（`decodeAudioData` → 自相关求 F0），但**必须先在真机上验证**。
给不出可靠结论时，就只做"听辨选择题"而不是"跟读评分"——
沿用英语站那条原则：**绝不给孩子看假的音准分**。

拼音还是语文的前置，两者共用同一份字表与拼音数据，**不要各维护一份**。

### 7.5 📖 语文

- 内容：认字（字音/字形/字义）、笔顺、组词、成语、古诗、看图说话、阅读理解
- 交互要点：笔顺动画 + 描红（SVG）、看拼音写汉字、组词连线、古诗填空、
  阅读理解（选择题为主）

#### 笔顺数据：可行，约 4 MB gzip（已核实）

| 资产 | 内容 | 体积 | 授权 |
| --- | --- | --- | --- |
| `hanzi-writer.min.js` | 笔顺动画库（纯代码） | **37 KB** | **MIT** ✅ |
| `hanzi-writer-data` | 每字一个 JSON（笔画 SVG path + 中线 median） | 3500 常用字 **10.27 MiB 原始 → 约 4 MB gzip**；单字中位数 2.9 KB | **Arphic Public License（APL）** |
| `makemeahanzi/graphics.txt` | 9574 字的笔画数据（同一批数据） | 29.3 MiB | APL |

**授权结论：APL 可用，且不传染**——它有一条明确的聚合条款
（"mere aggregation of another work not based on the Font … does not bring
the other work under the scope of this License"），所以**你的应用代码不受影响**。义务只有两条：

1. 原样保留 `ARPHICPL.TXT`；
2. 如果你**改动了数据**（重新编码、抽取字段），要加显著改动声明，并把改动后的文件同样以 APL 提供。

**要避开的坑**（都实测过）：

- 🚨 `hanzi-writer` 内置的 `charDataLoader` **写死了 jsDelivr CDN 地址**。
  这直接违反"零第三方 CDN"的约束，**必须覆盖 `charDataLoader` 指向自己的静态文件**
  （覆盖之后还顺便获得了离线能力）。
- 🚨 makemeahanzi README 里提到的 `svgs.tar.gz` **根本不存在**（404）——
  现成的动画 SVG 包拿不到，要自己从 `strokes` / `medians` 生成。
- ⚠️ makemeahanzi 的 `dictionary.txt` 是 **LGPL-3.0**（和 `graphics.txt` 的 APL 不同），
  不想背 LGPL 义务就别用它。

**字表用什么**：官方的《义务教育语文课程常用字表》**没找到授权干净、机器可读的版本**
（这条是 UNVERIFIED）。实际可用的替代：用**通用规范汉字表一级字表（3500 字）**
当目标集——它本身就是义务教育阶段的要求量，且和上面的拼音数据完美对齐（都是 8105）。

#### 呈现细节

坐标系统是 1024×1024，原点在**左上 (0,900)、右下 (1024,−124)**，
渲染时要写成 `<svg viewBox="0 0 1024 1024"><g transform="scale(1,-1) translate(0,-900)">`。
按需加载：**练到的字才下载，一个字约 1 KB gzip**，不必一次把 4 MB 全推给孩子。

### 7.6 ⌨️ 打字（**推荐的第一个新学科**）

- 为什么先做它：**不需要音频、不需要判题、不需要大数据集**，
  却完整走一遍"manifest → 平台层 → 进度 → 同步 → 徽章 → 家长摘要"的链路。
  用它验证学科契约，成本最低
- 内容：基准键位（ASDF JKL;）→ 上排 → 下排 → 数字 → 符号 → 短文 →
  **编程常用符号**（`(){}[]<>=+*/#:"'`）→ Python/C++ 关键字
- 指标：WPM / CPM、准确率、**每个键的错误率热力图**（哪根手指弱）
- 与其它学科的联动：打字段落可以直接取 Python 课的示例代码、英语单词、
  古诗，**一份内容多处用**——这是平台化真正的复利
- 中文打字**先不做**（涉及输入法，浏览器里拿不到可靠的候选交互），
  需要的话后续用"看拼音打词"的独立模式

### 7.7 ⚙️ C++（未来）

- 定位：承接 Python 之后的进阶（GESP 考级路线已有 Python 版）
- **关键架构点：把"运行代码"做成 `capabilities/judge` 的第二个实现**，
  学科本身不关心用的是 Pyodide 还是别的
- 编辑器可以直接复用 CodeMirror 的 `clike` 模式

#### ✅ 结论：可行，用 Runno，成本约 14.2 MB（brotli 传输）

技术选型已实测核实（不是估计）。**选 `Runno`（`taybenlor/runno`，MIT，活跃维护）**，
它自托管成静态文件，语言二进制放在一个普通 URL 前缀下（`/langs/`），不需要 CDN。

最关键的一点：**它的交互式 `std::cin` 用的是和你 Python `input()` 完全相同的机制**——
运行时里 `new SharedArrayBuffer(8*1024)`，WASI worker 在 `fd_read(stdin)` 路径里
`Atomics.wait(...)` 真阻塞，宿主用 `Atomics.store` + `Atomics.notify` 喂输入。
**所以"运行代码"这个能力抽象是成立的，而且 C++ 也必须在 COOP/COEP 下跑**
（`_headers` 里已经预留了 `/cpp/*`）。

实测体积（`Accept-Encoding: br` 实测，不是估算）：

| 文件 | 原始 | brotli 传输 |
| --- | --- | --- |
| `clang.wasm` | 31.2 MB | **7.54 MB** |
| `wasm-ld.wasm` | 19.5 MB | **4.87 MB** |
| `clang-fs.tar.gz`（sysroot） | 1.79 MB | ~1.79 MB |
| `@runno/runtime` dist | 1.7 MB（其中 WASI 引擎只 156 KB，其余是 CodeMirror） | — |
| **合计** | ~52 MB | **≈ 14.2 MB** |

**两个必须提前处理的问题**：

1. **工具链是 Clang 8.0.1（2019）、默认 `gnu++14`**，没有线程（`libpthread.a` 是 8 字节桩）、
   没有 `std::filesystem`。对小学 C++ 入门够用，但别指望教 C++17/20 特性。
2. 🚨 **Runno 默认给编译器传 `-Werror`**——任何 warning 都变成硬错误。
   对初学者是灾难（一个"变量未使用"就编译失败）。那个命令行数组是纯 JS，**自己删掉 `-Werror`**。

#### 被否决的方案（都核实过，别走弯路）

| 方案 | 为什么不行 |
| --- | --- |
| **JSCPP** | ⚠️ 看着最轻（136 KB gzip）但是**陷阱**：2021 年就停更了；作者自己的 README 写明 **classes/OOP、namespace、多文件都没实现**——没有 `struct`/`class`/`std::string`/`std::vector`，**那不是 C++，只是带 `cin`/`cout` 的 C**。而且它的 `cin` **不是交互式**的：`stdio.drain()` 只在 include 时调一次，所有输入必须在 `main()` 前给完；缓冲区耗尽还会抛裸 `Error("EOF")`（白屏风险） |
| **binji/wasm-clang**（那个 demo） | 同一个 Clang 8，但 `stdinStr` 是预设字符串、`poll_oneoff`/`clock_time_get` 直接 `NotImplemented` → **没有交互式输入**。Runno 的二进制和它字节相同，但补上了 SAB stdin —— 所以直接用 Runno |
| **WASI SDK** | 我枚举了它**所有版本的所有发布资产**：只有 linux/macos/windows 的**原生**工具链（174–592 MB）+ sysroot，**根本不存在浏览器可用的 wasm clang**。走这条路等于自己编译 clang→wasm |
| **Cling** | 构建目标是 `host;NVPTX`，**没有 wasm target**，也没有 wasm 发布资产，README 还写着 nightly 快照不可用 |
| **Cheerp** | 原生 LLVM 分支，需要 Linux 自行构建，无发布资产 |

#### 值得关注的备选：`cppstudio-io/wasm-clang-runtime`

Apache-2.0，**Clang/LLD 22.1.8 + wasi-sdk 33**（现代 C++），而且**专门为
微信 XWEB / 老 Chrome / 鸿蒙 ArkWeb 提供了 `noeh` 回退构建**并做运行时特性探测——
这一点对国内小学生的设备很有价值。代价：约 20–25 MB 传输（README 称 74 MB → 20 MB，
`.gz` 要自己生成），且只有 1★，**成熟度 UNVERIFIED**。

**建议路径**：先用 Runno 把 M5 做出来（它成熟、MIT、机制和 Python 一致），
把 `judge` 能力的接口稳定下来；等这个备选项目成熟、或者确实需要现代 C++ 时，
**换实现即可——这正是把运行能力做成插件而不是写死的好处**。

#### 执行仍然分两步走（架构不变）

1. **先做不执行的题型**（读代码选输出、找错、填空、语法）——零体积、零风险，
   对小学生已经很有价值，而且不依赖上面任何一个方案
2. 再上 Runno 的执行能力：**必须按需懒加载**（孩子点了"运行"才下载 14 MB，
   并明确显示体积和进度），否则一个只想看题型的孩子也要为 14 MB 买单

## 8. 内容生产管线（把好习惯制度化）

Python 站最强的一点是：**期望答案是跑出来的**。这条原则要推广成平台规范：

```
每个学科：
  content/<subject>/*.py (或 .mjs)      ← 题目"家族"源码
        │  tools/<subject>/gen.py        ← 生成 + 逐题校验（失败就报错、不写文件）
        ▼
  public/<subject>/data/*.js            ← 纯数据，懒加载
```

| 学科 | 校验方式 |
| --- | --- |
| 数学 | 用 Python 计算每道题的答案，与题目声明比对；自动生成干扰项 |
| 拼音 | 与字表/词典交叉校验（拼音、声调、多音字） |
| 语文 | 字表覆盖度、笔顺数据完整性、古诗文本与出处一致性 |
| 打字 | 语料字数/字符集校验（不出现打不出来的字、不含超纲符号） |
| Python | 已有：真跑参考答案，比对 stdout |
| 英语 | 已有：词库 schema 校验 + 音频与文本哈希一致性 |

统一入口：`tools/check-all.sh` 依次跑所有学科的 `--check`。
**`gen` 必须默认是"校验失败就不写文件"**——这是 Python 站已经验证过的做法。

老书签落到大厅多一次点击（无 PWA 可打断 Python 站，`/en/` 根本不动）。

同时改的：

- `public/index.html` / `public/js` / `public/css` → `public/python/`

- `public/_headers`：COOP/COEP 从 `/*` 收窄到 `/python/*` 与 `/cpp/*`
- `public/_redirects`：`/v2/*` 与 `/py/*` → `/python/`

**实测验证（118 项断言全绿）**：大厅 21 · 学堂 80 · 判题 8 · 成长 9；
内容脚本 54 课 / 132 示例 / 1318 题；`/` 与 `/en/` **不再发** COOP/COEP，

#### 两个部署（互不干扰）

这一阶段**故意不碰线上**，所以平台版跑在一个**独立的 Cloudflare Pages 项目**上：

| | 项目 | 地址 | 分支 | 状态 |
| --- | --- | --- | --- | --- |
| 现有线上 | `mian` | <https://mian.lihaiyang.net> | `main` | **完全没动**（`/` 仍是 30034 字节的 Python 应用） |
| 平台版 | `mian-platform` | <https://mian-platform.pages.dev> | `platform` | M0 已部署，118 项断言在真实边缘全绿 |

```bash
# 平台版（新项目）
wrangler pages deploy public --project-name mian-platform --branch platform

# 现有线上（不要动，除非确定要合并）
wrangler pages deploy public --project-name mian --branch main
```

`wrangler.toml` 里的项目名仍是 `mian`（保证 `main` 分支还能正常部署），
平台版靠 `--project-name` 覆盖。两个项目**共用同一个 D1**（同一张 `accounts` 表），
所以平台版能直接用现有的 8 位同步码登录——这也是验证同步链路的前提。

**等 M0 观察一段时间、确认没问题之后**，再把 `platform` 合进 `main` 并部署到线上。

### M1 — 抽平台层（最高风险，最需要纪律）

原计划：

1. 先写 `shared/core/profile.js` + `progress.js`，用**英语站**当第一个用户
   （它的 `progress.js` 更小、更规整，33KB）
2. e2e 全绿后再切**Python 站**（60KB，更复杂）
3. 再抽 `sync.js`：先英语（4 个实体）后 Python（6 个实体）
4. 最后抽 `ui.js` / `audio.js` / `srs.js` / `speech.js`
5. 加 `tools/stamp.mjs` 自动化版本号（见 6.2）

**纪律**：每一步都要"改一个学科 → 跑该学科全部 e2e → 绿了再动下一个"。
**任何一次 e2e 变红都立刻回滚那一步**，不要在红的基线上继续重构。

#### ✅ 已完成：平台内核（第 1、3、5 条的内核部分）

| 文件 | 职责 |
| --- | --- |
| `shared/core/store.js` | 命名空间化存储（`mian_<ns>__<key>`）、配额兜底、脏数据兜底 |
| `shared/core/progress.js` | 档案 / 经验等级 / 连续打卡 / 每日任务 / 徽章 / 奖牌 / 闯关任务 / onChange / 导出导入 |
| `shared/core/sync.js` | 通用云同步：rev + LWW + 墓碑，**实体由学科声明** |
| `functions/api/v1/sync.js` | 通用后端：所有学科落在一张 `sub_rows`，payload 是黑盒 |
| `tools/stamp.mjs` | 版本号按内容 hash 自动化（`--check` 可给部署前用） |

#### ⚠️ 未做：把两个老站迁到平台层上（原计划第 1、2、3、4 条的另一半）

**这是有意推迟的，不是漏了。** 理由：

1. **契约必须先被验证**。原计划让英语站当第一个用户，但那等于在一个契约
   还没被验证过的情况下，先动一个有真实孩子数据的线上站。实际做法反过来：
   先让**新学科（打字）**当第一个用户（见 M2），契约被 36 项 e2e 验证过之后，
   再考虑迁移——风险顺序是对的。
2. **老站的迁移不是"抽公共代码"，而是重写状态层**。英语站的 `progress.js`
   里有自己的 30 级曲线、69 枚徽章、49 枚奖牌、20 个任务，谓词写死在
   它自己的 stats 形状上；`cloud.js` 有 4 个专用实体。把它们改写成
   "声明 + 平台内核"要先重写这 100 多条声明，属于多天的工作量。
3. **收益是内在的，风险是外在的**。迁移老站**不会让孩子看到任何新东西**，
   却可能弄丢他们的进度和作品——而用户明确要求"保留老站"。
4. 老站刚经历 M0 的目录搬迁（P0/P1 之前还有一次同步大修，git log 里连续
   5 个云同步 bug），**现在最需要的是稳定，不是再一次重构**。

**将来要做的正确姿势**（`docs/代码库整理方案.md` 的 5.3 有同样的原则）：

- 一次只搬**一层**，而不是一次性把 progress + sync + ui 全换掉。
  建议顺序：先 `store`（纯读写，最容易验证）→ 再 `sync`（用英语站的
  `e2e_sync.mjs` + `e2e_offline.mjs` 当安全网）→ 最后才是 `progress`
- 存储键必须**先迁移再切换**：老站用 `codepanda_*` / `en_*`，平台层用
  `mian_*`。要在首次加载时做一次"旧键 → 新键"的拷贝，并且**保留旧键**
  一段时间（万一要回滚）
- 每一步都要能在**真机上用真实的 8 位同步码**跑一遍双向同步再上线

### M2 — 打字（验证契约）

用最简单的学科证明"加一科 = 加一个目录 + 一份 manifest"。
如果做打字时还需要改 `shared/` 的核心，说明契约没设计对，**回头修契约**。

#### ✅ 已完成（36 项 e2e）

- **内容**：`tools/typing/gen_lessons.py` 生成 17 关 / 6 阶段（2132 字符），
  生成前校验"字符能不能打出来 / 长度够不够 / 声明的键是否真的出现"。
  **校验当场抓到两个真实错误**（一关声明了 z/x/b 但文本里没有；另一关声明了
  `=` 但文本里没有）——修正的是内容，不是放宽校验。
- **学科特有部分**（`public/typing/`）：打字引擎（逐字符对错、退格、
  Enter、WPM、准确率）、键盘图（高亮下一个键 + 指法提示）、
  每键错误率热力图、成绩单（星级 + 奖励）、进度面板。
- **契约验收结果**：键盘岛**没有写一行**等级 / 打卡 / 徽章 / 奖牌 / 任务 /
  云同步 / 家长摘要的代码，这些全部正常工作（e2e 逐项断言了经验、完成次数、
  全对次数、字符数、连续打卡、最好速度、徽章发放、关卡记忆）。
  **"加一个学科 = 加一个目录 + 一份声明"成立。**
- 后端与数据库**一行都没改**，新学科直接用 `/api/v1/sync` + `sub_rows`。

**过程中修掉的三个真 bug**（都写进了代码注释）：

1. `subject.js` 里"没有 `Platform` 就 `return`"，导致学科页面（不加载大厅
   注册表）整个文件退出、成长规则没定义，`Progress.init()` 当场崩。
   → 大厅登记与成长规则是**两件独立的事**，不能共用一个提前返回。
2. 成绩单只保留**最后一次** `emit` 的返回值，所以永远看不到"打完这一关"
   本身给的经验。→ 多次 emit 的奖励要累加并去重。
3. 大厅没加载 `store.js`，用 `Store` 读进度的学科卡片显示不出"经验 N"。

**另外发现的一个体验问题**（截图才看出来）：打字时 WPM 一直显示 0，
因为原来"时间太短就不算"的阈值太粗。改成按 1 秒下限估算，
既不显示 0 也不会在头两个字爆出几百 WPM。

### M3 — 数学

内容量最大、需求最高。顺带验证 `srs` 能力跨学科复用（错题进记忆盒）。

### M4 — 拼音 → 语文

先拼音（数据少），再语文（笔顺数据重）。共用同一份字表。
**先做一条完整纵向切片**（一个声调 + 一组最小对立 + 音频 + 评测），
验证音频与评测方案，再灌内容。

### M5 — C++

先做不执行的题型（零体积、零风险）；再上 Runno 的执行能力（**按需懒加载 ≈14.2 MB**，
孩子点"运行"才下载并显示进度）。选型理由与被否决方案见 7.7。

### M6 — 家长中心

跨学科周报：各科用时/掌握度/薄弱点、连续打卡、可打印 A4。
**这是"发布在一处"真正的产品价值**——不是把两个站放一个域名，
而是家长在一个地方看到孩子的全部。
